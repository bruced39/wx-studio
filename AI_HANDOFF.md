## Emergency v0.9.6 editor startup hotfix

On Oct 15, 2026 the user reported v0.9.5 loaded an empty black stage, empty left tools and empty right inspector, even after restarting Streamlit. Root cause identified in `studio/ui.js`: `boot()` calls `buildTools()` before initializing `S.show`; `buildTools()` calls `setTool('select')`; v0.9.5 newly added `cur()?.bg?.type` inside `setTool()`. The optional chaining on `cur()` **does not guard the dereference inside `cur`**, which reads `S.show.scenes` when `S.show` is still null. This throws and aborts `boot`, leaving the UI blank. v0.9.6 changes only that cursor condition to use `S.show?.scenes?.[S.si]?.bg?.type`, which is safe before load.

- Verified with a focused V8 test calling `setTool('select')` when `S.show=null` and a syntax parse.
- **Do not add code paths accessing `cur()` before `S.show` is initialized.**
- v0.9.5 map changes are retained; still need live browser validation. Next ask user to refresh and confirm tools, scene panel and map return before further map changes.
- This is a startup hotfix, not verification of third-party Natural Earth coastline loading or browser pan behavior.

## v0.9.76 — Mapbox indefinite loading and GPU render recovery (ChatGPT, 2026-10-18)

- `settle()` used to test its 20-second timeout only *inside a Mapbox `render` callback*. ## v0.10.1.6 — MP4 export fix for real encoders: B-frames and malformed avcC (Claude, 2026-10-20)

**Context:** user exported one scene (`Scene_1_x1.mp4`, 150 frames, 1920×1080) from Chrome/Edge and the file would not play. Analysis of the file: (1) the real encoder emits **B-frames** (chunks in decode order with non-monotonic presentation timestamps) but the muxer wrote dts = pts, so stts had durations like 6000,1,9000,1… and the duration was 7.3 s instead of 5.0 s ("non monotonically increasing dts"); (2) the encoder's `decoderConfig.description` (avcC) was **malformed** — reserved bits wrong (`03 01` instead of `FF E1`), and the SPS and PPS each had their NAL header byte doubled (`67 67 64…`, `68 68 ce…`), so decoders reported "sps_id out of range / too many reference frames"; (3) samples carried in-band AUD, SPS, PPS and SEI NALs. This is **not scene-specific** – whole-show exports from the same encoder were equally broken. Earlier tests used a fake encoder with canned x264 output without B-frames and a standard avcC, so it was never caught.
**Changes (`studio/mp4.js`, `studio/export.js` one line, tests):**
- `videoTiming()`: decode times = sorted presentation times (strictly increasing), composition offsets (`ctts`, version 0, non-negative) and an `elst` edit list that skips the reorder delay so the first picture shows at 0. Streams with monotonic timestamps produce no `ctts`/`edts` — identical box layout to before. Video samples are interleaved in decode order.
- `Mp4Writer._prepare()`: splits samples into NAL units; collects in-band SPS/PPS, removes in-band SPS/PPS/AUD, and **builds a clean avcC** (version 1, profile/compat/level from the SPS, lengthSize 4, High-profile chroma/bit-depth fields parsed from the SPS). If there are no in-band headers, the encoder's description is read tolerantly and repaired (doubled header byte, wrong reserved bits); a valid description is copied verbatim; if nothing validates the original description/samples are used unchanged. `mp4.info` = `{avcC: 'built-from-stream'|'repaired'|'as-given', strippedNals, reordered}`; `Exporter.run` returns it as `mux`.
**Tests:** `tests/mp4_writer.test.js` 15 (7 new: real x264 B-frame stream muxed and compared frame-by-frame (md5) with the reference; Chrome-style in-band headers + the user's malformed avcC shape; repair without in-band headers; clean passthrough; no-B-frame layout unchanged; B-frames + AAC audio sync; duplicate timestamps) — the 4 real-bug cases fail on the old muxer. `tests/helpers/media.js` `h264Reordered()`/`frameHashes()`. `export_browser_check.py` fake encoder now emits Chrome-style output (reordered, in-band headers, bad avcC): 48/48 incl. ctts/elst present, frames shown at exactly i/30, ffmpeg decodes with 0 errors. ## v0.10.2 storage fix — branch `claude/v0.10.2-storage-fix` (Claude, 2026-10-22) — NOT released, VERSION unchanged (0.10.1.6), no Supabase files touched

**Live-test bug:** Scene 2 + a large uploaded background → Chrome showed "⚠ Not saved … storage is full" while the cloud chip said "Saved to cloud"; Firefox got Scene 2 with the default background. **Root cause (confirmed):** `autosave()` called `HK.changed()` (→ cloud `markDirty`) after `localStorage.setItem` inside the same `try`, so a `QuotaExceededError` skipped the cloud notification; the cloud engine builds from the live show, but was never told it changed.
**Changes:**
- `studio/ui.js` `autosave()`: the cloud notification now always fires (after the local attempt, in its own try/catch), plus a change counter `chgSeq` (`WX.cloud.changeSeq`).
- Large-show fallback (no migration, no format change): localStorage stays the normal autosave place with exactly the old JSON. When it refuses, the same JSON is written to a NEW IndexedDB database `wxstudio-autosave` (store `cur`, one record per autosave key, so it follows the account namespace) and a tiny marker `<autosave key>:idb` is set; if even the marker cannot be written the main key is replaced by the stub `{"wxIdbStub":1}` (a smaller value always fits). Boot reads the record from the database only when the marker/stub exists (synchronous boot is unchanged otherwise; 4 s timeout, falls back to the localStorage copy). When localStorage works again the marker is removed and the database record is kept but ignored (nothing is ever deleted by autosave). The status label stays "Saved" with a tooltip saying the larger storage was used; it shows "⚠ Not saved" only when BOTH stores fail. `legacyInfo`, `claimLegacy`, `clearAccountData`, `keepLocalCopy` understand the record. The Recent-autosave copies (own IndexedDB) and the portable `.wxshow` / Supabase formats are untouched.
- `studio/cloud_workspace.js` / `cloud_workspace_ui.js`: safety net — `host.changeSeq()`; the 20 s tick marks the show dirty if the editor changed without a notification, so the chip never keeps saying "Saved to cloud" for an unsynced change.
